# 何時需要你決定

工單不必寫得像規格書才能開工。Bridge 應該先處理能依專案慣例決定的細節；只有會明顯影響成果或驗收的問題，才需要你決定。提問時，也要說清楚差別、提出建議，讓你能在原本的操作畫面回答並繼續。

> **實作狀態（2026-11-06）**：本頁說明已定稿、尚在實作的提問流程，先處理「工單轉成合約」時的問題。writer 實作途中需要人工決定的情況，會在後續接入相同流程。下方會區分實際遇到的問題與新流程的示意。

## 為什麼要改：還沒開始寫程式，就被問個沒完

一次實測中，我們把三張簡單工單放進同一個目錄執行。其中一張只要求在 README 補上啟動方式：

```markdown
# README 補「如何啟動」一段

<!-- bridge:requested_work -->
## 要做的事
在 README.md 加一個「如何啟動」小節，列出安裝依賴與啟動的指令。

<!-- bridge:acceptance -->
## 驗收
1. README.md 裡有「如何啟動」小節。
2. 小節裡至少有一個可以直接複製執行的指令，放在程式碼區塊內。
```

三張工單都在轉成合約時停下來，還沒進入實作。終端機只顯示需要人工決定，以及結果檔的路徑。打開結果檔，才看到模型在問：「可以直接複製執行」是只要指令格式完整，還是必須能在這個專案執行成功？

我們把那句改得更明確，要求使用 `package.json` 裡實際存在的指令。第二輪又全部停下來，這次問的是：

- `npm install` 不在 `scripts` 裡，安裝指令是否也必須出現在那裡？
- 「三個小節」是剛好三個，還是至少三個？能不能另加簡介？
- 「最上面」是指檔案第一行，還是可以先有 `# Changelog` 標題？

每個問題都找得到追問的理由，但照這個方式執行，工單永遠補不完。模型每問一輪都要重新翻譯、核對，token 持續消耗，實作卻沒有開始。

原本的設計只處理了「發現歧義就停止」，沒有處理人接下來怎麼辦：哪些問題值得問、怎麼問、答完放在哪裡，以及如何繼續。假 CLI 測試和條件寫得很細的工單雖然通過，也沒有證明一般人能順利使用。

## 哪些問題需要問你

reviewer 會先指出可能的解讀與影響，再由 Bridge 依分級套用提問規則。不是模型一說「不確定」，就直接停下來。

| 類型 | 代表什麼 | 處理方式 |
|---|---|---|
| 影響驗收（`verification`） | 同一項要求，採用不同解讀會得到不同的通過結果 | 提請你決定 |
| 影響成果（`implementation`） | 採用不同做法，完成的功能或使用體驗會有明顯差別 | 提請你決定 |
| 一般細節（`preference`） | 不會實質改變成果或驗收 | 採用建議，記入合約與結果檔，不另外詢問 |

**專案或生態已有慣例時，優先採用慣例。** 例如 `npm install` 本來就不需要列在 `scripts` 裡；這類問題不必再交給人決定。採用的解讀仍會留下紀錄。

分級本身仍是模型的判斷，程式能限制的是如何處理這份判斷、問幾題、能不能繼續追問。這些限制不能證明模型每次都分對類，但能避免它無限制地把問題交回給你。

第一輪最多問 **3 題**，每題最多列 **3 種解讀或做法**。reviewer 依影響程度與不確定性排序，Bridge 只取前三題，其餘採用建議並留下紀錄。未提供必要分級或建議的回報，視為格式錯誤，不會直接變成給你的問題。

## 你可以選建議，也可以照自己的意思回答

問題會直接顯示在終端機，不必另外打開結果檔。透過 Claude Code 或 Codex 操作時，則由代理把問題呈現在它的提問介面。

以下是新流程的**畫面示意**；選項與來源標示用來說明格式，不是某個專案的實測結果：

```text
「有流光效果的按鈕」，你希望是哪一種？
  › 1. 背景顏色持續流動（建議；沿用專案現有的漸層動畫）
    2. 一道光帶掃過按鈕（模型知識，未查證）

    交給 AI 決定 → 採用建議，這張工單之後的細節也交給 AI
    自己說 → 用你自己的話描述
```

每個選項都要說明依據：專案裡已在使用、透過查詢取得，或只是模型既有知識。模型知識會標示「未查證」；無法交代依據的選項會被移除。若沒有可列出的做法，畫面會說明，並保留「交給 AI 決定」與「自己說」兩個出口。

目前規劃先使用專案內可讀取的內容與模型知識；在唯讀查詢工具接入前，模型聲稱查到的外部資料也只能標為「未查證」。之後才能把實際查到的 npm、GitHub 資料作為依據，不把模型記憶當成查詢結果。

你不必知道 CSS、動畫函式或套件名稱。回答「圓一點、慢一點」也可以，模型負責把意思整理成可執行的要求。即使工單只有「我要一個有流光效果的按鈕」，沒有驗收條件，模型也會連驗收方式一起提出，讓你選擇或交給 AI 決定。

## 答過的事，不再換個角度追問

提問限制由 Bridge 執行，不只寫在提示詞裡：

- **第一輪集中提出問題。** 不採用每次只問一題、下一輪再補新問題的方式。
- **選定的選項不再追問。** 第二輪起，只能針對你選「自己說」後、仍需釐清的那項內容提問；其他問題採用建議並記錄。
- **「交給 AI 決定」適用整張工單。** 之後遇到不同解讀，直接採用建議並標記「由 AI 決定」，不再回來問你。
- **問答最多 3 輪。** 模型看不到輪數上限。達到上限仍無法完成時，便以 `action_required` 結束，顯示並記錄問答內容。

因此，直接選定做法就會結束該項提問；只有自由回答仍不夠明確時，才需要下一輪。「交給 AI 決定」授權的是後續細節的選擇；工單內容更新後，仍須確認新的授權卡片。

這一階段的問答發生在候選合約產生之後、封存之前。合約封存後，不會再透過這個流程反覆詢問；writer 實作途中遇到問題的流程會另行接入。

## 回答寫回工單，再確認新版本

你的回答會留在工單裡，不必從對話或結果檔找回來重寫。Bridge 會把選定的內容追加到檔尾的補充說明區塊，保留你原本寫的句子：

```markdown
<!-- bridge:clarifications -->
## 補充說明
- 2026-11-06 11:52 關於「流光效果的按鈕」：沿用專案現有的漸層動畫。（由 AI 決定；後續細節也交給 AI 決定）
```

原本缺少驗收條件時，確認的驗收內容也會追加成 `<!-- bridge:acceptance -->` 區塊。

完整流程是：**回答問題 → Bridge 寫回工單 → 顯示新版授權卡片 → 你確認 → 重新翻譯、核對並封存合約 → 開始實作。** 這些步驟會在同一條 `start` 指令內接續，不必自己修改 Markdown 再重新輸入指令。

這裡會再請你確認一次，因為回答已經改變工單內容，你需要授權更新後的版本。若只是採用一般細節的建議，內容只記入合約與結果檔，不寫回工單，也不會因此多一次確認。

提問前，原本那次執行會先以 `action_required` 結束；回答寫回後，再依新版工單建立新的執行。一次執行多張工單時，會先跑完並列出總表，再集中處理需要回答的工單；重新開工時，已交付的會跳過。

問答途中按 **Ctrl+C 或 Esc** 可以離開。Bridge 會等整批問題都答完才寫入，因此中途離開不會把未完成的回答寫進工單。下次執行 `start` 會依磁碟上的工單重新開始，不接續上次問答。

## 設計參考與 Bridge 的差異

這套流程參考既有工具的提問方式，但 Bridge 多了一個需要保留的步驟：**回答改變工單後，必須重新確認授權。**

| 參考做法 | 來源 | Bridge 如何採用 |
|---|---|---|
| 只問會實質影響實作或驗證的問題，依影響與不確定性排序，限制題數 | [GitHub spec-kit 的 clarify 指令](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md) | 第一輪最多 3 題，由程式限制 |
| 提供少量選項、優先列出建議，允許自由回答 | [Codex 的提問工具定義](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/request_user_input_spec.rs) | 每題最多 3 種解讀或做法，另有「交給 AI 決定」與「自己說」 |
| 將回答寫回規格，保留已決定的內容 | [spec-kit 的 Clarifications 流程](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md) | 追加到工單自己的補充說明區塊，不改寫原文 |
| 依執行模式決定是否等待回答，限制提問者 | [Codex 的提問工具處理流程](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/request_user_input.rs) | 由 Bridge 控制提問時機，再透過終端機或代理介面呈現 |

spec-kit 通常逐題提問；Bridge 的問題來自獨立、唯讀的 reviewer。每次回答後，都要由 writer 重新翻譯，再由 reviewer 核對，會增加模型呼叫成本。因此 Bridge 將問題集中在第一輪，並限制後續追問。

以下則是 Bridge 自己訂的規則，並非上述工具已有相同機制：

- 選「交給 AI 決定」後，整張工單的後續細節都採用建議。
- 第二輪起，只能追問使用者自由回答、仍待釐清的內容。
- reviewer 逐題標示影響類型，由程式決定如何處理。
- 每輪使用新的工作階段，透過問題引用的工單位置辨認是否為同一件事。

## 總結

提問應該幫助你釐清會影響成果的選擇，答完就能繼續。Bridge 限制題數與追問範圍，並把答案留在工單裡，讓你用自己的話交代需求，也能確認最後授權的是什麼。

如果團隊經常被問到相同的事，可以整理自己的知識庫，讓代理在提問前先有依據可查。內容可以從這幾類開始：

- **專案慣例與術語**：常用元件、文件格式、團隊對特定用語的定義。
- **過去的決策與理由**：哪些做法已經選定、適用什麼情境，以及哪些方案不採用。
- **已驗收的範例**：完成的工單、對應成果與驗收方式，讓模型知道團隊認可的成果長什麼樣。

現階段可以先將相關文件或範例的引用放進工單，確保 reviewer 能以唯讀方式查閱。資料要標明來源與適用範圍，並隨決策更新，才不會讓舊答案成為新的誤解。也可以定期回看問答紀錄，找出反覆出現、值得補進知識庫的內容。

Bridge 後續規劃接入團隊知識庫，讓 reviewer 能檢索過去的合約、判定與補充說明，減少重複詢問。目前保留紀錄還不等於具備自動檢索能力；知識庫能提供判斷依據，新的需求或實質差異仍需要由你決定。
