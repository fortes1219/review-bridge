# ユーザーの判断が必要なとき

作業を始めるために、依頼を細かな仕様書に仕上げる必要はありません。プロジェクトの慣例で決められることは Bridge が処理し、成果や検証結果に大きく影響することだけをユーザーに確認する。その際は、選択肢の違いと推奨案を示し、今使っている画面で回答して作業を続けられるようにする、というのがこの設計の方針です。

> **実装状況（2026年11月6日時点）**：このページでは、設計が確定し、実装を進めている確認フローを説明します。まずは作業指示をコントラクトに変換する段階の質問が対象です。writer が実装中に判断を求める場合も、後から同じフローに接続する予定です。以下では、実際のテストで起きた問題と、新しいフローの表示例を区別しています。

## 課題：コードを書く前に、質問が終わらない

ある動作確認で、簡単な作業指示を 3 件、同じフォルダーに入れて実行しました。そのうち 1 件は、README に起動手順を追加するだけの依頼でした。

```markdown
# README に起動手順を追加する

<!-- bridge:requested_work -->
## 依頼内容
README.md に「起動方法」の節を追加し、依存関係のインストールと起動に使うコマンドを記載する。

<!-- bridge:acceptance -->
## 完了条件
1. README.md に「起動方法」の節がある。
2. その節に、コピーして実行できるコマンドが少なくとも 1 つ、コードブロック内に記載されている。
```

3 件ともコントラクトへの変換中に停止し、実装には進みませんでした。ターミナルに表示されたのは、ユーザーの判断が必要なことと、結果ファイルのパスだけです。ファイルを開いて初めて、「コピーして実行できる」とは、コマンドの記述が完結していればよいのか、それともこのプロジェクトで実際に成功する必要があるのか、と尋ねられていることがわかりました。

そこで、`package.json` に実在するコマンドを使うよう、条件を具体的に書き直しました。それでも 2 回目も全件停止し、今度は次のような質問が出ました。

- `npm install` は `scripts` にない。インストール用コマンドも、そこに定義する必要があるのか。
- 「3 つの節」とは、ちょうど 3 つか、3 つ以上か。別に導入文を追加してよいのか。
- 「一番上」とはファイルの 1 行目か。その前に `# Changelog` という見出しを置いてもよいのか。

どの質問にも、確認する理由はつけられます。しかし、この進め方では作業指示をいつまで補足しても終わりません。質問のたびにコントラクトの作成と確認をやり直し、トークンだけを消費して、実装は始まらないままでした。

元の設計は「曖昧なら止める」までしか扱っていませんでした。何を質問すべきか、どう聞くか、回答をどこに残すか、その後どう再開するかが欠けていたのです。CLI を模したテストや、条件を細かく書いた作業指示が通っても、ユーザーが無理なく使えることの確認にはなっていませんでした。

## どのようなことを確認するのか

reviewer は、考えられる解釈とその影響を示します。Bridge は分類ごとのルールに従って処理します。モデルが「不確か」と報告しただけで、そのまま作業を止めるわけではありません。

| 分類 | 意味 | 対応 |
|---|---|---|
| 検証に影響する（`verification`） | 同じ要件でも、解釈によって合否が変わる | ユーザーに確認する |
| 成果に影響する（`implementation`） | 方法によって、機能や使い勝手に明確な差が出る | ユーザーに確認する |
| 細部の違い（`preference`） | 成果や合否を実質的には変えない | 推奨案を採用してコントラクトと結果ファイルに記録し、質問しない |

**プロジェクトやエコシステムに定着した慣例があれば、それを優先します。** たとえば、`npm install` は `scripts` に定義する必要がありません。このようなことまでユーザーに判断を求めず、採用した解釈を記録します。

分類自体はモデルの判断です。コードで制御できるのは、その判断の扱い、質問数、追加質問を許す条件です。モデルが毎回正しく分類する保証にはなりませんが、際限なく判断をユーザーに戻すことは防げます。

初回の質問は最大 **3 問**、各問の解釈や方法は最大 **3 案**です。reviewer が影響の大きさと不確かさで優先順位をつけ、Bridge は上位 3 問だけを提示します。残りは推奨案を採用し、記録します。必要な分類や推奨案がない報告は形式エラーとして扱い、そのまま質問にはしません。

## 推奨案を選んでも、自分の言葉で答えてもよい

質問はターミナルに直接表示されます。結果ファイルを別に開く必要はありません。Claude Code や Codex 経由で操作している場合は、エージェントの質問画面で回答します。

以下は新しいフローの**表示例**です。選択肢や根拠の表記は形式を説明するためのもので、実際のプロジェクトで得られた結果ではありません。

```text
「光が動くボタン」は、どのようなイメージですか？
  › 1. 背景の色がゆっくり変化する（推奨：プロジェクトで使っているグラデーションのアニメーションを流用）
    2. 一筋の光がボタンの上を通り過ぎる（モデルの知識・未検証）

    AI に任せる → 推奨案を採用し、この作業指示の残りの細部も AI に任せる
    自分の言葉で伝える → 希望する見た目や動きを入力する
```

各選択肢には、プロジェクトで採用済みなのか、調べて得た情報なのか、モデルの知識なのか、根拠を添えます。モデルの知識は「未検証」と表示し、根拠を示せない案は除外します。候補がなくなった場合はその旨を説明し、「AI に任せる」と「自分の言葉で伝える」は引き続き選べるようにします。

初期段階では、読み取り可能なプロジェクト内の情報とモデルの知識を使う設計です。読み取り専用の検索ツールを接続するまでは、モデルが外部で調べたと主張する情報も「未検証」と扱います。npm や GitHub で実際に取得した情報を根拠にできるのは、その連携ができてからです。モデルの記憶を検索結果として扱うことはしません。

CSS やアニメーション関数、パッケージ名を知っている必要はありません。「もう少し丸く、ゆっくり」と答えれば、モデルが実行できる要件に整理します。「光が動くボタンがほしい」という一文だけで完了条件がない場合も、モデルが確認方法まで提案します。案を選ぶことも、AI に任せることもできます。

## 回答済みのことを、聞き方を変えて問い直さない

次の制限は、プロンプトへの指示だけでなく Bridge のコードで適用します。

- **最初にまとめて質問する。** 毎回 1 問ずつ聞き、次のラウンドで新しい質問を追加する進め方にはしません。
- **選択済みの案は問い直さない。** 2 ラウンド目以降に確認できるのは、ユーザーが自由入力した回答のうち、まだ不明な点だけです。それ以外は推奨案を採用し、記録します。
- **「AI に任せる」は作業指示全体に適用する。** 以後の解釈の違いは推奨案で進め、「AI が判断」と記録します。再びユーザーには尋ねません。
- **質問と回答は最大 3 ラウンド。** モデルには上限を知らせません。上限までに解決しなければ `action_required` で終了し、やり取りを表示・記録します。

案を選べば、その質問は終わりです。次のラウンドが必要になるのは、自由入力した回答をさらに確認する場合だけです。「AI に任せる」で委ねるのは以後の細部の判断であり、作業指示が更新された後は、新しい承認カードの確認が必要です。

この質問フローは、コントラクトの候補ができてから、内容を固定するまでの間に行います。固定後にこのフローで質問を繰り返すことはありません。writer が実装中に質問する場合の接続は、別途対応する予定です。

## 回答を作業指示に残し、新しい版を承認する

回答は作業指示に残ります。会話や結果ファイルから探し出し、自分で書き直す必要はありません。Bridge は元の文章を残したまま、ファイル末尾の専用ブロックに選択内容を追記します。

```markdown
<!-- bridge:clarifications -->
## 補足事項
- 2026-11-06 11:52 「光が動くボタン」は、プロジェクトで使っているグラデーションのアニメーションを流用する。（AI が判断。以後の細部も AI に任せる。）
```

完了条件がなかった場合は、確認した条件も `<!-- bridge:acceptance -->` ブロックとして追記します。

一連の流れは、**質問に答える → Bridge が作業指示に追記する → 新しい承認カードを表示する → ユーザーが承認する → コントラクトを再作成・確認・固定する → 実装を始める**、となります。同じ `start` コマンド内で続くため、自分で Markdown を編集してコマンドを実行し直す必要はありません。

再度の承認が必要なのは、回答によって作業指示の内容が変わるためです。細部の違いについて推奨案を採用するだけなら、コントラクトと結果ファイルへの記録にとどめます。作業指示には追記せず、それを理由に承認を増やすこともありません。

質問する前に、元の run は `action_required` で終了します。回答を追記した後、更新後の作業指示から新しい run を作成します。複数件をまとめて実行する場合は、まず全件の実行と一覧表示を終え、その後に回答が必要な作業指示をまとめて扱います。再開時は完了済みのものをスキップします。

回答中に **Ctrl+C または Esc** を押すと終了できます。すべての質問に答え終わってから書き込むため、途中で終了しても回答の一部だけが作業指示に残ることはありません。次の `start` はディスク上のファイルを読み直して最初から進み、前回の質問の続きにはなりません。

## 参考にした設計と Bridge 独自のルール

このフローは既存ツールの質問方法を参考にしています。Bridge では加えて、**回答で作業指示が変わったら、更新内容を再承認する**手順を維持する必要があります。

| 参考にした方法 | 出典 | Bridge での使い方 |
|---|---|---|
| 実装や検証に実質的な影響があることだけを質問し、影響と不確かさで並べ、質問数を絞る | [GitHub spec-kit の clarify コマンド](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md) | 初回を最大 3 問にコードで制限する |
| 少数の選択肢を示し、推奨案を先に置き、自由入力も受け付ける | [Codex の質問ツール定義](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/request_user_input_spec.rs) | 最大 3 案に加え、「AI に任せる」「自分の言葉で伝える」を用意する |
| 回答を仕様に書き戻し、決定事項を残す | [spec-kit の Clarifications フロー](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md) | 元の文章を書き換えず、作業指示の補足ブロックに追記する |
| 質問できる主体や、実行モードに応じて回答を待つかどうかを制御する | [Codex の質問ツールの処理](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/request_user_input.rs) | Bridge が質問のタイミングを制御し、ターミナルまたはエージェントの画面に表示する |

spec-kit は通常 1 問ずつ確認します。Bridge の質問は、独立した読み取り専用の reviewer から来ます。回答のたびに writer がコントラクトを作り直し、reviewer が確認するため、モデル呼び出しが増えます。そのため、最初に質問をまとめ、追加質問の範囲を制限します。

以下は Bridge 独自のルールであり、上記のツールに同じ仕組みがあるわけではありません。

- 「AI に任せる」を選ぶと、その作業指示全体の残りの細部に推奨案を適用する。
- 2 ラウンド目以降は、自由入力した回答の不明点だけを確認する。
- reviewer が質問ごとに影響を分類し、コードで処理を決める。
- 各ラウンドで新しいセッションを使い、質問が参照する作業指示内の位置から同じ論点かどうかを判断する。

## まとめ

質問は成果を左右する選択を明らかにし、答えたら作業を進めるためのものです。Bridge は質問数と追加質問の範囲を制限し、回答を作業指示に残します。ユーザーは自分の言葉で依頼し、最後に何を承認したのかを確認できます。

同じことを何度も聞かれる場合は、エージェントが質問前に参照できるよう、チームのナレッジベースを用意すると役立ちます。まずは次のような内容から始められます。

- **プロジェクトの慣例と用語**：よく使うコンポーネント、文書の形式、チーム内での用語の意味。
- **過去の決定とその理由**：採用した方法、適用する場面、採用しないと決めた案。
- **完了を確認した実例**：過去の作業指示、成果、検証方法。チームが求める水準をモデルに伝える材料になります。

現時点では、関連する文書や実例への参照を作業指示に記載し、reviewer が読み取り専用で参照できるようにします。出典と適用範囲を明記し、決定が変わったら更新してください。古い回答が新しい誤解の原因になるのを防げます。質問と回答の履歴を定期的に見直すと、ナレッジベースに追加すべき内容も見えてきます。

Bridge では今後、チームのナレッジベースと連携し、reviewer が過去のコントラクト、判定、補足事項を検索できるようにする予定です。記録が残ることと、自動検索が使えることは別です。ナレッジベースは判断の根拠になりますが、新しい要件や実質的な違いは、引き続きユーザーが判断する必要があります。
